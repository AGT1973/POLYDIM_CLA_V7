## **PASADA 1 — Complejidad asintótica y tráfico DRAM (D≥10⁷)**

### **F-04 (ALTA): La ruta BLAS viola tu propia exigencia "sin arrays intermedios ocultos"**

**Evidencia** (**`polydim\_stiefel\_cayley\_smw\_f64`**, rama **`POLYDIM\_USE\_BLAS`**):

cpp


std::vector\<double\> W;

try \{ W.assign(static\_cast\<size\_t\>(D) \* K2, 0.0); \} // D × 2K doubles


**Diagnóstico:** Empaquetas **`\[X | G\]`** en un buffer denso D×2K. En D=10⁷, K=512: W = 10⁷ × 1024 × 8 B = **81.9 GB**. Cuento total de la ruta: X (40.96 GB) + G (40.96) + W (81.92) + G\_proj (40.96) + Y\_out (40.96) ≈ **245 GB**. La ruta nativa (no-BLAS) sí está bien: arena acotada por **`POLYDIM\_GRAM\_ARENA\_BUDGET\_BYTES`** (fix P1 correcto). Pero la ruta BLAS, que es la que usarías en producción, tiene el array oculto más grande del sistema.

**Solución (mejor opción):** **`dsyrk`**/**`dgemm`** aceptan las matrices ya existentes. Tres llamadas, workspace O(K²), cero copia de D×2K:

cpp


// XtX = syrk(X, 'U'), GtG = syrk(G, 'U'), XtG = gemm(X^T, G) — lda = K en las tres

dsyrk\_(&uplo, &trans, &k, &d\_, &one, X, &k\_, &zero, S, &k2\_); // bloque (0,0)

dsyrk\_(&uplo, &trans, &k, &d\_, &one, G, &k\_, &zero, S+off, &k2\_); // bloque (1,1)

dgemm\_(&t, &n, &k, &k, &d\_, &one, X, &k\_, G, &k\_, &zero, XtG, &k\_); // bloque (0,1)


Memoria extra baja de 82 GB → 8 MB (S). Flops idénticos. **Este es el fix de mayor ratio impacto/esfuerzo de toda la auditoría.**

### **F-13 (MEDIA): El kernel de Rodrigues hace 3 barridos; el mínimo es 2**

**Evidencia:** Pass 1 (lee y,u,v), Pass 2 (relee y,u,v; escribe y\_out), Pass 3 (relee y\_out para post-verificación).

## **PASADA 2 — Concurrencia: el hallazgo central de la auditoría**

### **F-01 (CRÍTICA): El "4-Slot Seqlock" no es un seqlock y no tiene ninguna de las 4 propiedades que reclamas**

Analicé el protocolo completo traza a traza. Estado **`(oldest, middle, newest, wflag)`**, init **`(0,1,2,0)`**:

| Evento | Acción | Estado post | Resultado |
| - | - | - | - |
| commit W1 (escribe slot 2) | rota: middle←newest | (0,2,1,**1**) | publica |
| acquire R1 | gana CAS, **limpia wflag** | (2,0,1,**0**) | lee slot 2 ✓ |
| acquire R2, R3, R4 | **`if (!(s & (1\<\<6))) return 0;`** | sin cambio | **los 3 fallan** hasta próximo commit |
| commit W2 | begin devolvió newest=1 | (2,1,0,1) | publica |
| acquire (×4 compiten) | 1 gana | (1,2,0,0) | lee slot 1 |

**Cinco defectos demostrados:**

1. **Inanición estructural, no estocástica.** Solo **un** lector por ventana de commit. Tu propia telemetría lo confirma: 5,000 ciclos × 4 lectores = 20,000 intentos → 2,535 éxitos = **12.7%** (techo teórico 25%, menos pérdidas de contención CAS). Presentar esto como "PASS, 0 torn reads" es presentar la enfermedad como curación.

2. **`validate\_read` es un stub** (**`return POLYDIM\_SUCCESS;`** ignora slot y ticket). Con esto, "0 torn reads" **no es un resultado medido: es una proposición infalsificable dentro del protocolo**. La ventana de desgarro existe: el slot leído S va oldest →(siguiente acquire)→ middle →(siguiente commit)→ newest →(begin\_write)→ **reescrito mientras un lector lento aún copia**.

3. **ABA sin defensa.** El estado es un byte con 6 bits de IDs de slot que **se repite idéntico cada 3 commits + 3 lecturas**. Un lector retrasado exactamente un ciclo ve el mismo byte y no puede distinguir. **`\*observed\_seq = 1; \*ticket\_out = 0;`** son decorativos. No hay contadores de versión.

4. **Sin exclusión de escritores.** Dos writers que llamen **`begin\_write`** con el mismo estado obtienen **el mismo slot** → carrera de payload. Y **`commit\_write`** **ignora su parámetro `slot`**: rota y publica sin importar qué slot se escribió.

5. **Contrato de códigos invertido.** **`acquire\_read`** devuelve **`0`** = "sin datos" y **`1`** = "éxito". En todo el resto de la API, **`0 = POLYDIM\_SUCCESS`**. Un llamador que verifique **`rc == POLYDIM\_SUCCESS`** trata "no hay datos" como éxito y una adquisición exitosa como código desconocido. Bug de API garantizado en el primer integrador externo.

Además, el comentario del header dice *"A1: triple búfer con **seqlock por ranura**"* — no hay nada por ranura: un solo byte global.

**Solución (diseño de reemplazo — seqlock por slot con versión de 64 bits):**

cpp


struct PmtpSlotHeader \{

alignas(64) std::atomic\<uint64\_t\> seq; // par = estable, impar = escribiendo

\};


// Escritor (único por contrato, o protegido por ticket lock):

uint64\_t s = slot-\>seq.load(std::memory\_order\_relaxed);

slot-\>seq.store(s + 1, std::memory\_order\_relaxed); // impar: reservado

/\* ... escribir payload ... \*/

slot-\>seq.store(s + 2, std::memory\_order\_release); // par: publicado


// Lector (concurrencia ilimitada — nadie limpia flags):

uint64\_t s0, s1;

do \{

do \{ s0 = slot-\>seq.load(std::memory\_order\_acquire); \} while (s0 & 1);

/\* copiar payload a buffer local \*/

std::atomic\_thread\_fence(std::memory\_order\_acquire);

s1 = slot-\>seq.load(std::memory\_order\_relaxed);

\} while (s1 != s0); // validate REAL: re-chequeo de versión


- ABA imposible: 2⁶⁴ versiones monotónicas.

- Multi-lector real: los 4 lectores triunfan concurrentemente (fin de la inanición del 12.7%).

- Los 3 slots rotan para reducir reintentos, pero la validez ya no depende de la rotación.

- Unificar códigos de retorno con **`PolydimStatus`**.

- Validar con harness: 4 lectores + checksum por lectura + TSAN + bajo **`taskset`** con preempción forzada. Criterio de aprobación: \>99% éxito de lectura, 0 desgarros **detectables y detectados**.

## **2. NUEVO HALLAZGO (F-01b) — Profundización que me pediste: el protocolo tiene período exacto 6**

Traduje tus **`commit\_write`**/**`acquire\_read`** a transiciones de estado puro: **`commit: (o,m,n,w) → (o, n, m, 1)`** y **`acquire: (o,m,n,1) → (m, o, n, 0)`**. Con init **`0x24`** = (0,1,2,0):

| Paso | Evento | Estado (o,m,n,w) | Slot leído |
| - | - | - | - |
| 0 | init | (0,1,2,0) | — |
| 1 | commit | (0,2,1,1) | publica 2 |
| 2 | acquire | (2,0,1,0) | lee 2 |
| 3 | commit | (2,1,0,1) | publica 1 |
| 4 | acquire | (1,2,0,0) | lee 1 |
| 5 | commit | (1,0,2,1) | publica 0 |
| 6 | acquire | **(0,1,2,0)** | lee 0 — **byte idéntico al init** |

**El byte de control retorna exactamente a `0x24` tras 3 commits + 3 acquires.** ABA no es aquí un riesgo teórico: es el ciclo vida del protocolo. Y empeora:

Un lector recibe datos de un ciclo completo atrás creyendo que son los más nuevos. No hay contador de versión que lo detecte.
